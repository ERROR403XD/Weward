# Weward 群文件保存与投递使用说明

日期：2026-11-09

## 本次增加的能力

监听群里的文件可以随消息保存，并在定时或手动投递时与文字、图片一起进入 ZIP。本人发送的文件也会保存，不要求 @。接收端只保存 collector 实际通过 HTTP POST 发来的字节，不连接微信，也不挂载微信数据目录。

消息页增加“文件”类型筛选，显示原文件名、体积和下载入口，可以按文件名搜索。中文文件名、同名文件和空文件均可处理；同名文件按消息身份隔离，不会相互覆盖。

## 设置方法

打开 WebUI 的“配置”，在“群文件保存”区域设置：

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| 保存群文件 | 开启 | 对所有监听群生效，包括本人消息 |
| 允许的文件后缀 | 留空 | 留空表示全部，也包含没有后缀的文件 |
| 单个文件最大体积 | 20 MiB | 可以调整，最大 32 MiB |

后缀可填写 `pdf, docx, xlsx, pptx, txt, zip`。逗号、中文逗号或空格可分隔多个后缀；大小写不敏感，`PDF`、`.pdf` 都会保存为 `pdf`。支持 `tar.gz` 这样的复合后缀，不使用 `*.pdf` 通配符。

体积按每个文件分别判断，1 MiB 为 1,048,576 字节。当前采集入站通过 Base64 JSON 传输，单请求上限为 64 MiB，因此单文件设置最多 32 MiB。它不是所有文件的累计存储配额，也不是投递 ZIP 的压缩后大小限制。

点击“保存文件设置”后，之后采集的消息使用新规则。已有文件、已入队消息及已生成的待重试包保持原样。关闭保存不会删除历史文件；扩大后缀范围或提高体积限制，也不会自动补存以前被跳过的文件。

## 未保存的文件会怎样

只有微信桌面已经下载到本地的文件才能读取。本功能不会替微信下载尚未落地的附件，也不会自动发送微信消息。

不符后缀、超过体积上限或关闭保存时，消息仍会保存和投递，但只包含文件名及跳过原因。WeBox 在复制到 shared 目录前执行过滤，collector 在读取时再次检查实际大小，避免消息声明体积不准确导致超限保存。

符合规则但尚未下载完整、无法读取或缺少文件的消息，使用从消息时间起约一分钟的等待窗口。超过窗口后记录不可用原因，继续后续消息，不无限等待单个文件。历史文件如果采集时已经超过窗口，会直接记录当时的可用状态。错误记录不会自动变成可下载文件。

保存限制不控制微信客户端本身的下载及原始文件占用。collector 的队列保存文件快照，receiver 保存独立文件字节，已生成 ZIP 也需要存储空间；当前没有自动删除历史文件的保留期策略。

## 投递包内容

ZIP 直传和 multipart 两种投递方式都包含群文件，原有请求头、text 字段和回执规则继续有效。

```text
messages.json
images/<事件ID>.png
files/<事件ID>/报告.pdf
```

文件消息的 `file` 对象含 `status`、`filename`、`size`、`sha256` 和相对路径 `path`。可用文件的 `status` 为 `available`；过滤掉的文件为 `skipped`，不可用的文件为 `unavailable`，这两类保留原因但没有文件条目。

打包时会核验文件大小与 SHA256。已保存文件如果缺失或损坏，整个批次失败并显示错误，不会假装已经发送。图片与群文件合计达到每批 32 MiB 的媒体目标后拆分批次，每批最多 500 条消息。每个任务仍有独立游标，只在外部成功回执验证通过后推进。

失败重试、进程重启或修改任务配置都不会改写已经生成的包；同一批次继续发送相同文件字节。外部接收程序若需要处理新附件，应读取 `file.path`；原有 `messages.json` schema_version 保持为 1。

## 升级和回退

本功能包含 collector、receiver 和 WeBox compat3 的配套变更。开发基线为 `94458e4b67bad5e701e2013758f5524f5e1c69bf`，源码交付通过 Weward GitHub 仓库，本说明随源码维护。

部署方应从 GitHub 获取本轮提交，在自己的部署现场完成本地构建和验证：

1. 备份现有 collector、receiver 数据库和部署配置；暂停投递并等待正在进行的请求结束。
2. 按 README 运行 WeBox 准备脚本，生成 `weward-webox:8ca042c-wx4.1.1.8-compat3`。已有 `.env` 若覆盖 `WEBOX_IMAGE`，也要更新到 compat3。
3. 先更新 receiver，再更新 collector。receiver 自动追加文件存储列并回填旧文件名搜索索引，不改变既有事件身份、序号、接收时间、投递包和游标。
4. collector 重建后核实微信登录，必要时在桌面和手机确认。新 collector 依赖 compat3 文件策略接口，不继续搭配 compat2。
5. 在实际监听群发送一个允许的小文件，确认页面可下载、文件哈希一致，再向实际外部接收系统试投递并核对包内附件和回执。

旧文件消息仍可阅读和投递，但没有收到过的字节不会被补造。需要回退时，暂停任务并等请求结束，使用原版本和升级前数据库备份；直接换回旧程序会丢失对新增文件记录的完整处理能力。外部已经收到的数据不能通过本地回退撤销。

## 验证结果与当前状态

- 宿主及 Python 3.11 容器各通过 90 项标准库测试，含新增 16 项文件测试；旧数据库文件名索引迁移另经定向复核。
- 测试覆盖后缀与体积规则、32 MiB 文件 HTTP 传输、中文名、同名文件、空文件、源文件删除后的队列快照、响应丢失重试、重启去重、ZIP/multipart 文件投递、损坏文件阻止游标推进、旧数据迁移及配置修改与采集并发。
- WeBox 的 wechatdb、wechatapi、sharedmedia 三个 Go 包测试通过，包含文件策略传入、复制前过滤、实际大小核对、部分下载及有限等待。三份补丁在干净的临时源码树中可依次应用，生成源码与测试源码一致。
- 浏览器验证了设置保存与刷新后保留、真实 HTTP 文件下载、文件筛选，以及 1440、768、390、320 像素布局。
- 本轮完成开发与模拟验证，没有部署运行服务，也没有恢复真实微信登录。尚未验证真实微信群文件的本地下载、资源索引及端到端采集，不把上述模拟测试视为真实微信验收；本轮未重新构建完整微信桌面镜像。
